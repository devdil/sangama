# Qwen3.5-397B across three US states with drafts (30 September 2026)

Round 14. Round 13 measured one request at 10.4 tok/s across three states, without drafts. Drafts had only been measured across distance before the on-device rollback existed. This round measures them, and tests four changes that came out of a research pass on the remaining bottlenecks.

## Summary

- **One request with drafts: 28–49 tok/s, against 12 plain.** Code reaches 46–49; prose 28–31. This is 2.3–4 times plain on the same fleet.
- **Asking for the most drafts is now safe.** The final stage picks the draft count per request. With 8 requested, prose ran at 28 tok/s where a fixed 8 gave 25–27, and code kept 49.
- **Drafts with several requests at once are not yet trustworthy.** Totals were higher (4 requests: 40 to 72–80 tok/s; 16 requests: 133 to 150–173), but 4 of 32 requests in two runs took on another request's text and stopped early. A likely cause was found and fixed after the fleet was gone. These totals are reported as unverified.
- **A client could not reconnect after idling.** Found and fixed during the round.
- **No result on QUIC under packet loss.** One link dropped packets early on, and TCP ran at 5.5 tok/s. QUIC was measured after the loss had stopped, so the two were never compared under the same conditions. Both ran at 12 tok/s on the clean link.

### The draft rule

Three versions ran on the fleet:

1. **Busy share of the engine.** Drafts were cut when the final stage was busy. It cut them where they still paid: 16 requests ran at 152 tok/s with it and 173 without.
2. **Tokens per second, one acceptance rate.** The stage estimates a pass as the time outside the engines plus a cost per position, and picks the count with the most tokens per pass time. With a single rate shared by all requests, code after prose drafted too little: 40 tok/s where 50 was available.
3. **The same with acceptance recorded per request and per draft length.** This is the table above.

The rule has only been measured where the network dominates. Its behaviour on a busy fleet in one datacenter, the case it was written for, is untested.

### Fault: requests mixing text

In two drafted runs at 16 requests, 2 requests each ended early with text from another prompt, for example "…by splitting the capital city of Australia". Both runs used a rule that gives requests different draft counts. No run with a fixed count ended early, but those were not checked any other way.

- **Likely cause.** A device call that contains drafts must hold slots without a gap, or the engine's rollback states come out wrong (round 12). The check compared each frame only with the one before it, so a drafted frame could join a call that already had a gap between two plain frames. With every request drafting the same number this never arose.
- **Fix.** Commit `d003894`, with a unit test of the grouping. It has not been run on the 397B model.
- One request at a time is not affected: there is one session and nothing to mix with.

## Other findings

- **Reconnecting after idle.** A direct connection closes after three idle minutes. The client, on the relay's machine, then redialled each worker at every address it remembered, including the worker's own `127.0.0.1:9000`. The relay answers there, the dial ended with the wrong peer, and every request failed until the mesh was restarted. Commit `22f8d28` redials only the circuit and public addresses. After the fix a request succeeded after four idle minutes and after restarting a worker's mesh, though the log showed no reconnect in the first case, so the path was not clearly exercised.
- **Moving from relayed to direct connections** (commit `15c30ed`) worked: every peer's relayed connection was closed within two seconds of start, and no request failed at start-up, which had happened in round 13.
- **48 sessions with rollback depth 8 do not fit** in 96 GB; the context could not be created. 48 with depth 4 fit on the first two stages but left no room for the draft layer on the last. 32 with depth 2 fit.
- **Drafts beyond the rollback depth are very slow.** With depth 4, six and eight drafts fell back to saved snapshots and a pass took 300–530 ms.
- **A single frame costs more when many sessions are live**: 7–8 ms per stage against 4.7 ms alone. This fits the research finding that changing batch shapes stop the GPU from reusing its compiled graph. Not yet acted on.

## What was built this round

| Change | Commit | Measured effect |
|---|---|---|
| Hand-over from relayed to direct connections | `15c30ed` | No start-up failures; relayed connections closed at once |
| Draft layer runs once per device call for all sessions | `eafeca6` | Not isolated; drafted totals are unverified |
| At most one prompt frame per turn; batch size in traces | `eafeca6` | Not isolated |
| Draft count chosen per request | `049d974`, `d1d5924`, `3c14ca3` | Prose at 8 requested: 28 tok/s against 25–27 |

| No slot gaps in a call with drafts | `d003894` | Untested on the fleet |

## Limits

- One fleet, single runs, three prompts for one request and four for several.
- The middle stage was in Wisconsin, not Utah as in round 13, so the two rounds' plain speeds (12.2 and 10.4 tok/s) are not the same route.
- Whole-run totals include client start-up and the first token, so short runs understate steady throughput.

## Next

1. Run the concurrent drafted cases again with the gap fix and compare every request's tokens with its solo drafted run.
2. Send the next pass from the last stage straight to the first, not through the client: an estimated 15 ms off each pass.
3. A small draft model at the client, running ahead of the large one: estimated 40–68 tok/s for one request.
4. Keep batch shapes stable so the GPU reuses its graph.
