# Qwen3.5-397B through a relay: many requests at once, and MTP drafts (30 September 2026)

Three questions about the same 20-stage pipeline as the [29 September run](qwen35-397b-relay-2026-09-29.md):

1. **Round 7:** how much total throughput does it give when many clients generate at once?
2. **Round 8:** how much faster is one request when the last stage drafts tokens with the model's own multi-token-prediction (MTP) head?
3. **Round 9:** do the two combine?

## Summary

- **Throughput scales with concurrent requests.** One request decodes at 1.25 tok/s on this fleet. 32 at once gave 35.6 tok/s in total, and the best run reached 90.9 tok/s with 51 requests. Each request kept its own speed up to about 50 at once.
- **MTP drafts cut the passes through the pipeline by 2.7–5.3×** and raised one request's decode speed by 1.2–2.2×, to 2.69 tok/s at best.
- **Drafts also work with many requests at once:** 48 requests with drafts gave 83.1 tok/s against 51.3 without, though the gain varied between runs and was absent at 32.
- **Correctness:** every concurrent request produced the same tokens as when run alone (96 of 96 in the largest run).
- **Output depends on how tokens are batched.** Drafted runs were fluent but often not token-identical to plain decoding. Plain decoding alone shows the same effect when only the prompt chunk size changes, so this comes from the model's numerics, not from drafting.
- **This fleet is slower than round 6** (1.25 against 5.4 tok/s for one request), because its machines are spread over three US states. The comparisons here are within this fleet.

## Setup

| | |
|---|---|
| Model | Qwen3.5-397B-A17B, Q4_K_M, 20 stages of 3 layers, llama.cpp on CUDA |
| Workers | 20 rented GPUs (RTX 4090, 5090, 3090 Ti, 5080, L4), 16 GiB budget each; the last stage has 30 GiB for round 8 |
| Network | Every hop through one relay in Nevada; no direct paths |
| Placement | 5 workers on the relay's host (about 1 ms), the rest 17–56 ms away in Nevada, California and Utah |
| One request | 800 ms per token (p50), 23 ms of it GPU compute |

**Why a new fleet.** The round-6 relay and ten of its workers were rented from one provider whose listings ended on the morning of 30 September. Vast.ai stops an instance when its listing ends, and it cannot be restarted until the provider relists it. The fleet was rebuilt on listings with at least two weeks left, which are further apart. Some listings report a wrong location: two "California" machines were 220 ms and over 400 ms from the relay per hop and were replaced. A TCP connect time can hide this behind a local proxy; timing a real server reply (the SSH banner) does not.

## Round 7: many requests at once

Each worker now holds up to 96 sessions, each in its own llama.cpp sequence (`--slots`). Every client ran one of four prompts; each request's tokens were compared with the same prompt run alone.

| Requests at once | Completed | Total tok/s (whole run) | Sum of decode tok/s | Per request, decode tok/s | First token, p50 | Same tokens as alone |
|---|---|---|---|---|---|---|
| 1 | 1 | 1.11 | 1.3 | 1.25 | 4.8 s | 1/1 |
| 2 | 2 | 2.08 | 2.4 | 1.18 | 6.3 s | 2/2 |
| 4 | 4 | 5.18 | 6.2 | 1.55 | 6.1 s | 4/4 |
| 8 | 8 | 7.89 | 9.8 | 1.22 | 8.4 s | 8/8 |
| 16 | 16 | 19.53 | 30 | 1.88 | 16.1 s | 16/16 |
| 32 | 32 | 35.59 | 60 | 1.87 | 20.3 s | 32/32 |
| 64 | 64 | 48.41 | 56.4 | 0.88 | 7.0 s | 64/64 |
| 96 | 96 | 56.62 | 67.6 | 0.70 | 13.5 s | 96/96 |
| 96 asked, 51 ran | 51 | 40.68 | **90.9** | 1.79 | 4.7 s | 51/51 |

- Rows 1–32: 64 tokens each, all clients started together. Rows 64 and 96: 128 tokens each, clients started 0.3 s apart.
- "Total" divides all tokens by the whole run, including prompts and start-up. "Sum of decode" adds each request's decode speed, which is the steady rate once all are running. For rows 1–32 it is the per-request median times the request count.
- The last row is a run where 45 clients failed at start-up (see limit 3 below) and the other 51 ran together.
- **Up to about 50 requests, each keeps its speed**, so throughput grows with the count. Past that, each request slows and the total stops rising. CPU was 10–20 % on every node and GPUs under 7 %, so the limit is not compute. It is not yet identified.
- **Memory:** 96 slots took 14.0–15.3 GiB per stage, including the 12.6 GiB of weights.

### Limits found and raised

1. **llama.cpp cached every layer for every session.** A stage allocated attention and recurrent state for all 60 layers, about 306 MB per session. It now keeps only its own layers' state: about 12 MB per session, plus 8 MB if the stage has an attention layer.
2. **Mesh limits sized for one session per worker.** A bridge forwarded 4 requests at once, a node served 8, kept 16 calls in flight, allowed 64 session claims and 1,200 requests per peer per minute. Each waiting session holds a result request open on the last stage, so these capped a route at 4, then 16, then about 48 sessions. They are now above the 256 sessions a worker can hold.
3. **The benchmark's own clients.** One client process per request opens 20 connections, so 50 processes exhausted the client mesh's 1,024 file descriptors. A real client would multiplex sessions in one process.

## Round 8: drafts from the model's MTP head

The published GGUF omits Qwen3.5's MTP layer, so it was converted from the original release into an MTP-only GGUF. The last stage loads it, drafts up to K tokens after each token it samples, and returns them with the result. The next pass verifies them in one trip. 64 tokens per run.

| Prompt | Drafts per step | Passes | Tokens per pass | Drafts accepted | Decode tok/s | Speed-up |
|---|---|---|---|---|---|---|
| Code | 0 | 64 | 1.00 | – | 1.25 | – |
| | 2 | 23 | 2.78 | 41 / 42 | 1.82 | 1.46× |
| | 4 | 15 | 4.27 | 49 / 55 | 2.29 | 1.83× |
| | 6 | 12 | 5.33 | 52 / 66 | **2.69** | **2.15×** |
| Explanation | 0 | 64 | 1.00 | – | 1.24 | – |
| | 2 | 29 | 2.21 | 35 / 55 | 1.43 | 1.15× |
| | 4 | 24 | 2.67 | 40 / 90 | 1.43 | 1.15× |
| | 6 | 20 | 3.20 | 44 / 105 | 1.60 | 1.29× |
| Factual | 0 | 64 | 1.00 | – | 1.22 | – |
| | 2 | 25 | 2.56 | 39 / 47 | 1.65 | 1.35× |
| | 4 | 24 | 2.67 | 40 / 83 | 1.44 | 1.18× |
| | 6 | 22 | 2.91 | 42 / 121 | 1.44 | 1.18× |

- **The head drafts well.** The first draft or two is almost always right (41 of 42 with two drafts on code). Later drafts in a chain are accepted less often.
- **A verify pass costs more than a plain pass**, which is why 5.3 tokens per pass gave 2.15× rather than 5.3×. A plain pass took about 0.8 s and a verify pass 1.5–2 s. Every stage saves its state before the batch and, after a rejection, restores it and replays the accepted tokens. Making that cheap is the next step.
- **Q4_K_M and Q8_0 heads perform the same:** with 4 drafts, Q8_0 accepted 48/59, 42/82 and 40/83 against Q4_K_M's 49/55, 40/90 and 40/83. The 5.7 GB Q4_K_M head is enough.
- **Memory:** the last stage used 19.5 GiB with the Q4_K_M head and 22.4 GiB with Q8_0, against about 15 GiB without.

### Output depends on batching

Drafted runs were often not token-identical to plain decoding: 2 of 9 Q4_K_M runs and 1 of 6 Q8_0 runs matched to the end. The texts are fluent and differ at close word choices, for example "iteratively." against "using an iterative approach.".

This is not caused by drafting. **Plain decoding with the prompt sent in 8-token chunks instead of 64 diverged at token 18**, the same position as the drafted runs, with no speculation involved. Repeating any run with the same settings gave identical tokens. So the output is deterministic for a given batching, but batching several positions together changes the arithmetic slightly, enough to flip a near-tie. On the dense Qwen3.5-0.8B model, drafted and plain runs matched in every local test.

Earlier reports said every configuration produced the same tokens. That held for the prompts and settings tested then, but it is not true in general for this model.

## Round 9: drafts and many requests together

The last stage held 96 sessions and the Q4_K_M MTP head (21.5 GiB). Each pair ran the same clients with drafts off and with 4 drafts per step, 128 tokens each, clients started 0.3 s apart.

| Requests at once | Drafts | Completed | Sum of decode tok/s | Per request, decode tok/s | Tokens per pass | Drafts accepted |
|---|---|---|---|---|---|---|
| 16 | off | 16 | 21.7 | 1.36 | 1.00 | – |
| 16 | 4 | 16 | **38.9** | 2.32 | 3.16 | 1400 / 2480 |
| 32 | off | 32 | 57.1 | 1.85 | 1.00 | – |
| 32 | 4 | 32 | 49.9 | 1.43 | 3.16 | 2800 / 4960 |
| 32, repeated | off | 32 | 56.5 | 1.76 | 1.00 | – |
| 32, repeated | 4 | 32 | 59.6 | 1.74 | 3.16 | 2800 / 4960 |
| 48 | off | 48 | 51.3 | 1.09 | 1.00 | – |
| 48 | 4 | 48 | **83.1** | 1.72 | 3.16 | 4200 / 7440 |

- **Drafts and concurrency work together:** every request completed in every run, and 56 % of drafts were accepted, the same as for one request.
- **The gain under load is not consistent.** Drafts gave 1.8x at 16 requests and 1.6x at 48, and nothing at 32 (0.87x, then 1.05x on a repeat). Each cell is one run, and plain runs themselves varied from 1.36 to 1.88 tok/s per request at 16 between this round and round 7. More repeats are needed before quoting a speed-up under load.
- Without drafts, every request matched its solo tokens. With drafts, a quarter did (4/16, 8/32, 12/48), for the batching reason described above.

## Operations

- **Replacing a worker** took 5–15 minutes: rent, download the stage, create an identity, join with a single-use invitation, update the stage's peer on every node, restart the mesh processes.
- **Two rented hosts could not reach Hugging Face or PyPI** and were replaced. One stage download failed a slice checksum and succeeded on retry.
- **A mesh process exits at start** if the portal's membership snapshot times out. The deploy script now checks and retries.
- **Mesh-only builds roll out without reloading models:** a CPU build, made in under two minutes on the relay box, replaced every mesh process four times during the run.

## What next

- **Cheaper rollback** for drafted tokens: save only the recurrent state and trim the attention cache, or keep per-position state during verification so a rejection needs no replay.
- **Find the limit near 50 concurrent requests.** Compute is idle, so it is in the request path: one stream per frame over each relayed connection, or each node's single event loop.
- **Batch sessions in one decode call** per stage, once the request path is no longer the limit.
- **Check listing end dates and real latency** before placing a stage on a machine, and move stages before a listing ends.
- **A client that multiplexes sessions** in one process, instead of one process per request.

The fleet was destroyed after round 9. The Q4_K_M MTP head is kept locally (`mtp-q4_k_m.gguf`, SHA-256 `5c01abdc7fb733c0f33f16f62dee287c52ddd2c7397f5b12ec024455b5d2c11b`); it is not published yet.
