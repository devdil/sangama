# Qwen3.5-397B in three large stages: the speed-up work streams, tested (30 September 2026)

Round 10 tests the work streams in [the production speed-up plan](../plans/production-speedup.md) on one fleet. It is a different kind of fleet from rounds 1–9: three 96 GB datacenter cards in one room instead of twenty 16 GB cards, so it shows what the same software does when hops are few and close.

## Summary

- **One request: 48–50 tokens per second plain, and up to 107 with drafts.** Rounds 7–9 ran one request at 1.25 tok/s on twenty spread-out machines, and round 6 at 5.4 on twenty machines near their relay.
- **Rejected drafts now cost nothing to undo.** Frames waited 0.2–0.4 ms per pass inside workers, rollback included, against about 36 ms per stage for the saved-state path in round 8.
- **Total throughput was about 120 tok/s plain and 180 with drafts, and batching raised plain throughput to 403 tok/s at 48 requests and 449 at 64** (round 11). The per-stage timing showed the limit: frames queued at the last stage, whose GPU handled them one at a time.
- **Direct connections work** after one fix, and cut transit from 6.2 to 5.1 ms per pass. The relay was in the same room, so this fleet cannot show the gain across distance.
- **Every concurrent plain request matched the same request run alone** (48 of 48). Drafted output again differs from plain output at close word choices, as described in the round 7–9 report.

### Where a pass goes

| | Plain pass | Pass with 6 drafts (code) |
|---|---|---|
| GPU compute, three stages | 14.3 ms | 31.0 ms |
| Waiting inside workers, rollback included | 0.3 ms | 0.4 ms |
| Transit: network and mesh processes, four hops | 6.2 ms | 5.6 ms |
| Total | 20.7 ms | 36.1 ms |

Each row is a median over the run's passes, so the parts need not add up to the total exactly.

- **Compute is now the larger part**, the opposite of the twenty-stage fleets, where it was 1–3 % of a pass.
- **A drafted pass costs more because it computes more.** Verifying seven positions takes about twice the compute of one, and the last stage also runs the MTP head. None of the extra is rollback.
- **Two or four drafts is the useful range for prose.** Six drafts were accepted less than half the time on the explanation and factual prompts and ran slower than four.

### The ceiling, located

In a run with 48 requests, one frame's trace reads:

| Stage | Compute | Wait before computing |
|---|---|---|
| 0 | 6.9 ms | 0.17 ms |
| 1 | 5.5 ms | 0.01 ms |
| 2 (last) | 8.1 ms | **344 ms** |

Each session waits for its previous token before sending the next frame, so the whole queue gathers at the slowest stage. The last stage takes 8.1 ms per frame under load, and one frame at a time that is 123 frames per second, which is the ceiling measured. Mesh event loops were 0–1 % busy.

This is a different limit from the one in rounds 7–9, where twenty 3-layer stages computed a frame in about 1 ms each and throughput stopped near 90 passes per second with everything idle. That one is still unexplained and was not re-tested here.

## Round 11: iterating on the measured limits

A second session on the same kind of fleet (three 96 GB cards and a relay in one datacenter), changing one thing at a time. Plain decoding, 128 tokens per request, direct connections.

| Step | Change | 16 requests | 48 requests | Kept |
|---|---|---|---|---|
| Start | One frame per device call | 119 tok/s | 119 | – |
| 1 | Stop drafting below a confidence cutoff (0.3, 0.5, 0.75) | single request: no gain | – | No |
| 2 | Waiting sessions' frames in one device call | 174 | failed, then 184 | Yes |
| 3 | Batch in slot order | 184 | 210 | Yes |
| 4 | Limit a batch to sessions ÷ stages | 195 | 222 | Yes |
| 5 | One shared attention buffer for all sessions | 263 | **403** | Yes, as a switch |
| 6 | 64 requests | – | **449** (64 requests) | – |

Totals are the sum of each request's decode speed. Over whole runs, prompts and start-up included, 48 requests gave 300 tok/s and 64 gave 339.

- **Step 1, no gain.** The first version summed `exp()` over the 250,000-token vocabulary for every draft, which cost more than it saved. With that fixed, a cutoff of 0.3 trimmed almost nothing (115 drafts either way on the code prompt) and higher cutoffs cut good drafts along with bad ones. The MTP head's confidence does not separate the two well enough. A draft costs about 5 ms and saves about 20 ms when accepted.
- **Step 2.** A batch of 31 prompts (866 positions) exceeded the engine's 512-position batch and failed; batches are now split to fit.
- **Steps 3 and 5.** With a separate attention buffer per session, llama.cpp merges sequences into one step only when their ids are consecutive and increasing. Sorting by slot made a full batch one step; a shared buffer removed the rule, so any waiting sessions merge. A batch of 16 then costs about 20 ms per stage.
- **Step 4.** One batch of everything waiting makes all sessions move through the route as a single wave, so one stage works while the others idle. Smaller batches run back to back keep all three busy. This needed step 5 to pay off.
- **One request is unchanged** at 48–50 tok/s plain and 80–102 with 4 drafts; these changes act on load.

### Correctness under batching

- **Plain batched requests contain no text from other sessions**, in every run checked. About a third match their solo tokens exactly; the rest differ at the near-tie positions described earlier (for example "**Pipeline parallelism**" against "Pipeline parallelism" as the first token). Batching several sessions changes the arithmetic the same way batching several positions does.
- **Drafts with batching and the shared buffer were wrong in this session, and their numbers are discarded.** 13 of 32 drafted requests contained text from another session's prompt, and some ended after 15–21 tokens. The cause, reproduced locally on Qwen3.5-0.8B: with a shared buffer the engine merges sequences whose ids have gaps between them, and the rollback states written in such a step are wrong. Each pair of the three features works; all three together gave 0 of 8 requests matching. Drafted frames now stay in runs of adjacent slots (commit `96bb022`), which restores 7 of 8 locally. This fix has not run on the 397B fleet.

## Round 12: drafts with batching, re-validated

A third session on the same kind of fleet, with the adjacent-slot fix, 16 sessions per worker, rollback depth 4, the shared attention buffer and batching. 16 requests at once, 256 tokens each.

| Drafts per step | Whole run: tokens ÷ time | Tokens per pass | Drafts accepted | Same tokens as alone | Text from another session |
|---|---|---|---|---|---|
| 0 | **233 tok/s** (17.6 s) | 1.00 | – | 7 / 16 | 0 |
| 2 | 201 tok/s (20.3 s) | 2.54 | 2468 / 3149 | 3 / 16 | 0 |
| 4 | 174 tok/s (23.5 s) | 3.26 | 2839 / 4929 | 8 / 16 | 0 |

One request alone on this build: 46.8 tok/s plain and 100.4 with 4 drafts.

- **The fix holds on the 397B model.** No drafted request contained another session's text or ended early, and drafted requests matched their solo tokens about as often as plain ones.
- **Under load with batching, drafts lower total throughput.** Batching made the GPU the limit, and every rejected draft spends it. Drafted frames also batch less well: they only merge in runs of adjacent slots, and the MTP head still drafts one session at a time (72 ms of the last stage's pass with 4 drafts, against 13 ms plain).
- **So drafts are for a lightly loaded route.** One request gains 2x from them; sixteen lose 14–25 %. A worker could refuse draft requests when its queue is long.

**A caution on the throughput figures.** The sum of each request's decode speed overstates throughput when requests finish at different times, which drafts cause: it read 379 tok/s for the 4-draft row above, whose whole run delivered 174. For plain runs, where all requests run for the same time, the two agree more closely (273 against 233 here; 403 against 300 and 449 against 339 in round 11, where start-up was staggered). Whole-run figures are the conservative ones.

### Still open after round 11

- **Batch the MTP head's drafting across sessions.** It still drafts one session at a time on the last stage.
- **A request lost at start-up:** one request failed with "Peer disconnected" while a relayed connection was being closed in favour of a direct one. A retry, or closing only idle connections, would avoid it.

## What each work stream showed

| Stream | Result | Status |
|---|---|---|
| A. Cheap rollback | Wait inside workers, rollback included, was 0.2–0.4 ms per pass. Drafts now give a net gain even with no network delay to hide behind. | Done. The plan's gate (drafted pass within 10 % of plain) assumed the network dominates; here compute does, so a drafted pass costs 1.6–2.3× a plain one in real compute. |
| B. Direct connections | All nodes ran with direct connections and none relayed. Transit fell from 6.2 to 5.1 ms per pass. | Works. Needed a fix: libp2p's hole punching ignores configured public addresses, so nodes now dial them. Gain across distance not measured. |
| C. Placement by delay | `scripts/route-order.py` orders a chain and flags rentals that end soon. | Built and unit-tested. Not exercised: three machines in one room. |
| D. Find the ceiling | Per-stage receive times and mesh load lines located this fleet's ceiling in one run. Relay circuits are no longer cut at 1 GiB. | Instrumentation done. The twenty-stage ceiling remains open. |
| E. Per-hop overhead | Transit is about 1.3 ms per hop here. | Only the cheap clean-up was made. Moving the mesh into the worker would save at most a few ms per pass on this fleet. |
| F. Fewer, larger stages | 3 stages ran one request at 48 tok/s. | Done by layout alone; no code was needed. |
| G. Batching in a stage | Built in round 11: 119 to 403 tok/s at 48 requests, plain. | Done. With drafts it was wrong at first; the fix was validated in round 12, where drafts under load proved slower than plain. |

## Operations

- **Setup took under an hour** from renting to the first token: a CUDA build from scratch on a 384-thread box, three 82 GB stages, identities and invitations.
- **Stage downloads were the slow part.** One slice at a time gave about 23 MB/s from Hugging Face; six at once finished each stage in minutes.
- **Hole punching failed with `NoAddresses`** until nodes dialled advertised addresses themselves.

## Limits of this test

- One fleet, one run per cell, three prompts.
- It is not the consumer-hardware case. A 96 GB card costs about $1.90 an hour to rent, and three of them cost half of what twenty small cards did.
- Direct connections, placement and the twenty-stage ceiling need a fleet with distance between machines.

## What next

Batching and a confidence cutoff, which this list first named, were built and tested in rounds 11 and 12 above.

1. **Batch the MTP head's drafting across sessions**, and turn drafts off when a worker's queue is long.
2. **Repeat every cell** several times; these are single runs.
3. **A middle layout on 24–48 GB cards** (6–10 stages) with distance between machines, to test direct connections and placement where they matter.
