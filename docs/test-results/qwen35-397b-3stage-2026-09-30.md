# Qwen3.5-397B in three large stages: the speed-up work streams, tested (30 September 2026)

Round 10 tests the work streams in [the production speed-up plan](../plans/production-speedup.md) on one fleet. It is a different kind of fleet from rounds 1–9: three 96 GB datacenter cards in one room instead of twenty 16 GB cards, so it shows what the same software does when hops are few and close.

## Summary

- **One request: 48–50 tokens per second plain, and up to 107 with drafts.** Rounds 7–9 ran one request at 1.25 tok/s on twenty spread-out machines, and round 6 at 5.4 on twenty machines near their relay.
- **Rejected drafts now cost nothing to undo.** Frames waited 0.2–0.4 ms per pass inside workers, rollback included, against about 36 ms per stage for the saved-state path in round 8.
- **Total throughput tops out at about 120 tok/s plain and 180 with drafts.** The new per-stage timing shows why: frames queue at the last stage, whose GPU handles them one at a time.
- **Direct connections work** after one fix, and cut transit from 6.2 to 5.1 ms per pass. The relay was in the same room, so this fleet cannot show the gain across distance.
- **Every concurrent plain request matched the same request run alone** (48 of 48). Drafted output again differs from plain output at close word choices, as described in the round 7–9 report.

### Where a pass goes

| | Plain pass | Pass with 6 drafts (code) |
|---|---|---|
| GPU compute, three stages | 14.3 ms | 31.0 ms |
| Waiting inside workers, rollback included | 0.3 ms | 0.4 ms |
| Transit: network and mesh processes, four hops | 6.2 ms | 5.6 ms |
| Total | 20.7 ms | 36.1 ms |

- **Compute is now the larger part**, the opposite of the twenty-stage fleets, where it was 1–3 % of a pass.
- **A drafted pass costs more because it computes more.** Verifying seven positions takes about twice the compute of one, and the last stage also runs the MTP head. None of the extra is rollback.
- **Two or four drafts is the useful range for prose.** Six drafts were accepted less than half the time on the explanation and factual prompts and ran slower than four.

### The ceiling, located

In a run with 48 requests, one frame's trace reads:

| Stage | Compute | Wait before computing |
|---|---|---|
| 0 | 6.9 ms | 0.17 ms |
| 1 | 5.5 ms | 0.01 ms |
| 2 (last) | 8.1 ms | **344 ms** |

Each session waits for its previous token before sending the next frame, so the whole queue gathers at the slowest stage. The last stage takes 8.1 ms per frame under load, and one frame at a time that is 123 frames per second, which is the ceiling measured. Mesh event loops were 0–1 % busy.

This is a different limit from the one in rounds 7–9, where twenty 3-layer stages computed a frame in about 1 ms each and throughput stopped near 90 passes per second with everything idle. That one is still unexplained and was not re-tested here.

## What each work stream showed

| Stream | Result | Status |
|---|---|---|
| A. Cheap rollback | Wait inside workers, rollback included, was 0.2–0.4 ms per pass. Drafts now give a net gain even with no network delay to hide behind. | Done. The plan's gate (drafted pass within 10 % of plain) assumed the network dominates; here compute does, so a drafted pass costs 1.6–2.3× a plain one in real compute. |
| B. Direct connections | All nodes ran with direct connections and none relayed. Transit fell from 6.2 to 5.1 ms per pass. | Works. Needed a fix: libp2p's hole punching ignores configured public addresses, so nodes now dial them. Gain across distance not measured. |
| C. Placement by delay | `scripts/route-order.py` orders a chain and flags rentals that end soon. | Built and unit-tested. Not exercised: three machines in one room. |
| D. Find the ceiling | Per-stage receive times and mesh load lines located this fleet's ceiling in one run. Relay circuits are no longer cut at 1 GiB. | Instrumentation done. The twenty-stage ceiling remains open. |
| E. Per-hop overhead | Transit is about 1.3 ms per hop here. | Only the cheap clean-up was made. Moving the mesh into the worker would save at most a few ms per pass on this fleet. |
| F. Fewer, larger stages | 3 stages ran one request at 48 tok/s. | Done by layout alone; no code was needed. |
| G. Batching in a stage | Not built. | Now justified by data: the last stage is the limit, and it is the one stage where llama.cpp can batch sequences without a patch. |

## Operations

- **Setup took under an hour** from renting to the first token: a CUDA build from scratch on a 384-thread box, three 82 GB stages, identities and invitations.
- **Stage downloads were the slow part.** One slice at a time gave about 23 MB/s from Hugging Face; six at once finished each stage in minutes.
- **Hole punching failed with `NoAddresses`** until nodes dialled advertised addresses themselves.

## Limits of this test

- One fleet, one run per cell, three prompts.
- It is not the consumer-hardware case. A 96 GB card costs about $1.90 an hour to rent, and three of them cost half of what twenty small cards did.
- Direct connections, placement and the twenty-stage ceiling need a fleet with distance between machines.

## What next

1. **Batch waiting sessions on the last stage** in one decode call. It is the measured limit on a close fleet.
2. **Cap drafts by confidence**, so prose stops paying for a fifth and sixth draft that are usually rejected. The worker already takes a threshold (`SANGAMA_MTP_P_MIN`); it was not used here.
3. **A middle layout on 24–48 GB cards** (6–10 stages) with distance between machines, to test direct connections and placement where they matter.
