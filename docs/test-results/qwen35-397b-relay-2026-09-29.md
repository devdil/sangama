# Qwen3.5-397B on 20 rented GPUs, relay only, 2026-09-29

The first run of a frontier-size model on Sangama: Qwen3.5-397B-A17B (Q4_K_M, 60 layers) split into 20 stages, one per machine, with every hop forced through a Circuit Relay v2 server. Each worker was capped at 16 GiB, to stand in for a well-equipped personal machine rather than a server.

Raw data: [per-machine metrics](qwen35-397b-relay-2026-09-29/metrics/) (`scripts/sysmetrics.py summarize`, one file per machine, per phase) and [per-run reports](qwen35-397b-relay-2026-09-29/runs/) (`generate` JSON with the per-stage breakdown).

## Setup

| | |
|---|---|
| Model | `unsloth/Qwen3.5-397B-A17B-GGUF` Q4_K_M, published as per-layer slices on Hugging Face and assembled on each worker ([model slices](../model-slices.md)) |
| Stages | 20 × 3 layers; stage 0 also holds the embedding (13.2 GB file), stage 19 the output head |
| Workers | 20 Vast.ai containers in California: 12 × RTX 4090 (24 GB), 8 × RTX 5090 (32 GB); 12–256 CPU cores; 63 GB–1 TB RAM |
| Engine | llama.cpp (CUDA), `--memory-budget-mib 16384` |
| Relay and client | One separate container in California, two peer identities |
| Network | Admitted mesh (`sangama-private-v1`), live portal membership, `force_relay` on every node: no direct or hole-punched paths |
| Route per token | client → relay → w00 → relay → w01 → … → w19, and the sampled token back along the same chain: 21 relayed hops each way |

## Round 6: 9x overall, and speculative decoding

The last stage (w19) was 29 ms from the relay, and as the last stage it pays that distance twice per token: once receiving from the previous stage, and again when the client collects the result. It was replaced by a machine in the relay's datacenter.

| Run | Baseline | Round 5 | **Round 6** |
|---|---|---|---|
| Short answer (34-token prompt) | 0.58 / 7.5 s | 4.14 / 1.6 s | **5.46 / 1.3 s** |
| 128-token answer | 0.57 / 7.9 s | 4.35 / 2.3 s | **5.42 / 1.9 s** |
| Code | 0.67 / 5.8 s | 4.24 / 1.9 s | **5.49 / 1.4 s** |
| Factual | 0.62 / 5.8 s | 3.99 / 1.9 s | **4.94 / 1.7 s** |
| 99-token prompt | 0.67 / 11.1 s | 3.85 / 2.8 s | **5.07 / 2.1 s** |
| 237-token prompt | 0.63 / 14.1 s | 3.72 / 4.2 s | **4.98 / 4.0 s** |
| 459-token prompt | timed out | 4.77 / 4.3 s | **5.29 / 6.2 s** |

- **Per token (p50): 181–200 ms**, from about 1,500 ms at baseline. Every run gave the same tokens as the first F32 run.
- **What's left is geography.** Hops between machines in the relay's datacenter take 0–4 ms. Hops touching workers elsewhere take 9–44 ms, and no further machines were available in that datacenter.
- **Estimated ceiling:** all 20 stages in one datacenter would take roughly 21 hops × 3 ms plus 22 ms of compute, about 85 ms, or ~12 tok/s. This is not measured.

**Speculative decoding: correct, but slower with prompt-lookup drafts.**
- **Implementation:**
  - The client drafts up to 4 tokens per step by prompt lookup (copying what followed the latest earlier occurrence of the last 2–4 tokens).
  - Each stage snapshots its sequence state before a speculative batch (`llama_state_seq_get_data`, including the linear-attention recurrent state).
  - The last stage returns the greedy token for every position.
  - When fewer drafts are accepted, the next frame's position tells each stage to restore its snapshot and replay the accepted inputs locally, with no extra network trip.
- **Correctness:** every speculative run reproduced the non-speculative tokens exactly.
- **Speed:** the model accepted only 5–26% of these drafts (7 of 38 for code, 6 of 24 for the summary, 2 of 23 for the essay). The snapshot, restore and replay on all 20 stages then cost more than the saved passes.
  - Warm A/B runs: code 2.1–2.7 tok/s without speculation vs 1.3–1.4 with it; summary 1.6–2.8 vs 0.6–1.2.
  - These were measured before round 6, while network time happened to be higher.
- **Status:** speculation stays off by default (`SANGAMA_SPECULATE=0`). Making it pay needs a better draft source: Qwen3.5's own multi-token-prediction layer, with a reported 70–80% acceptance. Its tensors are not in the published slices yet. It would also need cheaper snapshots (llama.cpp can save only the recurrent state, `LLAMA_STATE_SEQ_FLAGS_PARTIAL_ONLY`, and trim attention KV instead).

Per-token p50 is now 208–268 ms, from about 1,500 ms at baseline. GPU compute is still 21 ms. Every round produced the same tokens as the first F32 run.

**Round 3: stability and observability** (no speed change on its own)
- **Stage timestamps.** Each stage now records when it started, so the report shows every hop's network time for the first token (`first_trace`).
- **Clients stuck after peer restarts.** When a worker's mesh restarted, the client dialled a cached address instead of the relay circuit, and never recovered. Identify had cached the worker's advertised listen address, `127.0.0.1:9000`, which on the relay's machine is the relay itself (`WrongPeerId`). The mesh now dials the circuit address explicitly, and relay-only nodes no longer advertise listen addresses. After all 20 worker meshes were restarted, the client reconnected to all of them unaided.
- **Large yamux windows** (each new substream gets an 8 MiB receive window at once) and `tcp_slow_start_after_idle=0`. Neither changed the numbers measurably.

**Round 4: pipelined prefill**
- The prompt now goes in 64-token chunks. The client pushes each chunk as soon as the first stage has accepted the previous one, so stages work on different chunks at the same time. Each worker sends through one ordered queue, so chunks cannot overtake each other.
- Chunk-size sweep, time to first token (237 / 459-token prompts): 502 tokens (one frame) 8.7 / 14.3 s; 128 tokens 5.1 / 6.5 s; **64 tokens 3.3 / 4.3 s**; 32 tokens 4.3 / 4.7 s.
- Remaining variance traced to two hops through one host with a slow link to the relay (w02, w03): 0.6–1.6 s for the last chunk, versus 10–40 ms elsewhere.

**Round 5: latency-aware placement**
- TCP connect time to the relay ranked the workers: w18 49 ms, w17 41 ms, w16 36 ms, w19 29 ms, w02/w03 18 ms, everyone else under 10 ms.
- The three farthest (w16–w18) were replaced by machines in the relay's datacenter, sub-millisecond away. They downloaded their stages, joined, and the old identities were revoked, with the route serving throughout.
- Decode roughly doubled again, to 3.7–4.8 tok/s.
- This is the choice a scheduler should make automatically: prefer peers close to the relay (or to each other). The allocator does not do it yet; here it was done by hand from measurements.

**Tried and not usable here: direct connections.** With `force_relay` off, hole punching (DCUtR) failed on every pair with `NoAddresses`. Vast containers have no inbound port mapping, so peers have no confirmed external address. Published measurements put DCUtR success at about 70% on real home networks; testing that needs different machines.

## Optimisation round 2: 3–4x faster decode

Two changes, same 20 machines and relay (one stage moved to a replacement host after its host reclaimed the GPU), same prompts:

1. **Detached forwarding.** Each stage replies as soon as it has passed the frame on, and the last stage keeps the sampled token for the client, which collects it with one request (`/v1/qwen/result`). Before, every stage waited for its downstream reply, so each token crossed every hop twice. Petals v2 made the same change.
2. **BF16 hidden states on the wire.** This halves the bytes per hop, so a 4 MiB frame holds twice as many prompt tokens. Stages still compute in F32.

Also added: libp2p sends the protocol proposal together with the first request data on each new substream (`V1Lazy`), and the last stage holds a result request open for up to 50 s.

- **Same output.** Every configuration produced token-for-token the same answer as the first F32 run (`gen`). The small-model check on a Mac was also identical under BF16.
- **Decode: 3–4x.** Per-token p50 dropped from about 1,500 ms to 370–520 ms, while GPU compute stayed at 21 ms.
  - Detached forwarding alone gave about 2.2x, matching one network crossing per hop instead of two.
  - BF16 gave another 1.4–2x on decode, more than halving an 8 KB saving would suggest. Our inference: a 16 KB frame no longer fits in what the new substream can send in its first round trip, while 8 KB does. We have not verified this.
- **Prefill.** Long prompts now complete. The 459-token prompt takes 22.6 s to its first token, bounded by throughput on the far hops: each request opens a new yamux stream at a 256 KB window.

Raw reports: `runs/opt-*.json` (detached) and `runs/bf-*.json` (detached + BF16).

### New issues seen in this round

- **The host at one address reclaimed two GPUs** (the original w04, then w03). A second replacement host could not reach Hugging Face or the Python package CDN at all and was discarded. Replacements came from a host that already had working downloads.
- **One dead peer blocked every new circuit.** After w03 died, the client mesh failed all new circuits with `Peer disconnected or unavailable`, even to healthy workers, until it was restarted. Fixed in round 3: the cause was a stale cached address, not the connect-request cap.

### What is left (from the research)

- **MTP speculative decoding.** Qwen3.5-397B has a multi-token-prediction layer and llama.cpp supports it, with a reported ~2–2.4x at 70–80% acceptance. Each stage would need to roll back its linear-attention (Gated DeltaNet) state when drafts are rejected.
- **Persistent streams per hop.** Keeping a stream open lets its window grow, which should cut prefill several-fold.
- **Placement.** Use regional relays or hole-punched direct paths (DCUtR succeeds about 70% of the time in published measurements), and prefer peers near the relay. Three far workers alone cost about 0.5 s per token in the baseline.
- **Concurrent sessions.** The GPUs are still more than 90% idle, so serving several users at once would multiply total throughput. It would not make a single stream faster.

## Where each token's time goes (baseline)

- **GPU compute: 21 ms per token, 1.4 %.** Each 3-layer stage takes 0.7–1.4 ms; only 17B of the 397B parameters are active per token.
- **Network: about 1.5 s per token, 98.6 %.** The measured relayed round trip per hop, with a decode-sized (16 KB) payload, adds up to 1.03 s over the 21 hops. Per-hop handling (HTTP, framing, the local worker call) makes up the rest.
- **Geography dominates.** Hops between workers close to the relay took 3–40 ms, but three workers were 150–175 ms from it. Those three hops alone cost about 0.5 s per token. A token must cross every stage in order, so the slowest links set the speed.

| Network | 0.13 Mbit/s in and out | 4 MB per worker for the whole run |

Loading a stage from local disk took 6–16 s. Hosts with a fast link downloaded and verified a stage's ~12 GB of slices from Hugging Face in 5–6.5 minutes (250–350 Mbit/s).

In short, a 397B model fits on 20 machines with 16 GB each, and those machines sit almost idle. The limit is the latency of the relayed path, not compute or bandwidth.

## Bugs found and fixed

1. **Route check rejected sliced models.** The client required every stage to use the same GGUF file, which is right for one published GGUF but wrong for per-layer slices, where each stage is a different file by design. Sliced stages are now pinned by their manifest digests instead.
2. **The relay silently dropped reservations.** libp2p's default relay rate limits refill one reservation token per minute per IP, and one per two minutes per peer. The relay saw all 21 container peers as one NAT address, and members renew every ~90 s, so the per-IP bucket emptied in three rounds. After that, 16 of 20 workers were unreachable (`NoReservation`). A single peer would also have exhausted its own bucket after about three hours. The relay now sets explicit limits.
3. **The DHT used relayed circuits as N² traffic.** Every node ran Kademlia in server mode, so each node queried and stored offers on every other node through the relay. 20 workers opened about 170 circuits (the route needs 39), the relay's per-connection capacity overflowed, and the relayed round trip grew from ~6 ms to ~350 ms, or ~1 s per request. Nodes behind a relay are now DHT clients and keep their offers on the relay. Latency fell to 2–40 ms.
4. **No `TCP_NODELAY` on the HTTP servers.** axum does not set it on accepted sockets, so a response written in parts can wait for the peer's delayed ACK. It is now set on the worker and bridge servers. The measured gain here was about 10 %, less than expected: the relay path dominated.

## Operational events

- **A host died.** The first relay box stopped answering on every port during a binary download and did not return after a reboot. It was replaced with a new box, a new identity and new invitations.
- **A worker was reclaimed.** The host stopped w04 mid-test and could not restart it ("required resources are currently unavailable"). A replacement downloaded its stage in 5 minutes, joined with a new identity, and the old identity was revoked. The route then gave tokens identical to the earlier runs.
- **One CPU build serves every mesh process.** The relay, the client and every worker's mesh process need no GPU build, so a 1-minute CPU build replaced them all without reloading the model.

## Known limits

- **Prompts above ~240 tokens could time out (baseline; fixed in the optimisation round).** A prompt was sent in chunks of up to 251 tokens (a 4 MB F32 hidden state per hop). Through the far relayed hops one full chunk took 14 s to over 30 s, and a single 30 s client timeout covered the whole chained forward. With detached forwarding the client waits up to 58 s for each result, and BF16 halves the bytes per hop, so a 459-token prompt now takes 22.6 s to its first token.
- **Credit receipts.** Workers logged `portal refused credit receipt status=403` for every session. Inference is unaffected, but credit accounting did not record this run.
- **One relay, one region.** All traffic crossed one relay in one region. Relays near each group of workers, or direct paths where NAT allows, would remove most of the 1.5 s.

## Cost

The fleet (20 workers and the relay box) cost about $13 per hour on Vast.ai. Each worker was $0.24–$0.91 per hour.
