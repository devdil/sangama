Qwen3.5-397B across three US states, with guesses

30 September 2026, round 14

In our previous test, one request crossing three US states ran at about 10 tokens per second. Almost all of each trip was network time. When the model guesses the next few tokens and one trip checks them all, the same network time yields several tokens. We had not measured that across a distance since making wrong guesses cheap to undo.

Result:

  • One request: 28 to 49 tokens per second with guesses, against 12 without. Code is at the top of that range, prose at the bottom.
  • Several requests at once: totals were higher with guesses, but a fault appeared and we do not trust those numbers yet.

How many guesses to make

More guesses help code, where most are right, and hurt prose, where the later ones are usually wrong and still cost computing. With a fixed eight guesses, code ran at 50 tokens per second and prose at 25 to 27.

The last machine now decides for each request. It keeps a record of how often that request's first guess, first two, and so on were right, estimates how long a trip takes with each count, and picks the count that gives the most tokens per second. With eight asked for, prose ran at 28 and code kept 49.

We tried two simpler rules first. One cut guesses whenever the last GPU was busy, which lost speed here. One used a single success rate for all requests, which made code guess too little after prose. The rule has only been tested where the network dominates.

The fault. In two of the runs with guesses, 2 of 16 requests picked up text from another request and stopped early. One answer about splitting a model across computers ended with "the capital city of Australia".

  • Likely cause: when the requests in one step guess different numbers of tokens, the step could be put together in a way the model runtime's undo does not handle. With every request guessing the same number, as in earlier tests, this did not arise.
  • Status: we found and fixed this after the machines were returned, so the fix is not yet tested on the large model. Until it is, the numbers in the right-hand column stand as unverified.
  • One request at a time is not affected.

What else the testing caught

  • A client could not reconnect after a few idle minutes. It redialled each machine at every address it remembered, including an address that only means something on that machine itself. On our test client that address reached the relay, and every request failed. It now redials only public addresses and the relay route.
  • Memory sets the number of requests a machine can hold. 48 requests with room to undo eight guesses did not fit in 96 GB. 32 with room for two did.
  • Guessing more than the machines can undo is very slow. Six or eight guesses with room for four took 300 to 530 ms per trip.

QUIC and a bad link

Early in the test, the link to one machine was dropping packets, and one request over TCP ran at 5.5 tokens per second. By the time we switched to QUIC the link had recovered, so we did not get to compare the two under loss. On the clean link both ran at 12.

Limits of this test

  • One fleet, single runs, three prompts.
  • The middle machine was in Wisconsin, not Utah as in the previous test, so the two tests' plain speeds are not the same route.
  • Output with guesses can differ from plain output at close word choices, as before.

Next

  • Re-run guesses with several requests with the fix, checking every request against its solo run.
  • Send each next step from the last machine straight to the first, not through the user's computer.
  • A small model on the user's computer that guesses ahead of the large one.
