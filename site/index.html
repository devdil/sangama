Sangama

Sangama (संगम) means confluence: computers coming together to run one AI model.

How it works | Architecture | Results | Hardware | Roadmap | Contact | Source code

Sangama is an open-source program, written in Rust, that splits a language model's layers across several computers: Macs, GPUs and ordinary CPUs. A model too large for any one device can then run across several, with encrypted, invitation-only connections between them.

Status: experimental. It runs on an invite-only network of trusted computers. It has run Qwen3.5-397B across 20 GPUs with 16 GB each (results), and is tested in depth with a small model (Qwen2.5-0.5B-Instruct). It is released under the MIT License.

How it works

A language model predicts each next piece of text (a token) by passing numbers through a stack of layers. Sangama gives each computer a contiguous slice of those layers.

  +----------+   tokens    +-------------------+  activations  +-------------------+
  |  Client  | ----------> |     Worker A      | ------------> |     Worker B      |
  |          |             |  layers 0 - 11    |               |  layers 12 - 23   |
  |          |             |  (e.g. a Mac)     |               |  (e.g. a GPU)     |
  +----------+             +-------------------+               +-------------------+
       ^                                                                 |
       |                     next token, then repeat                     |
       +-----------------------------------------------------------------+
  1. Contribute. Each worker loads only the slice of the model it serves, sized to the memory it offers.
  2. Route. A client checks that its workers cover every layer in order, reserves them, and sends the prompt through the chain.
  3. Generate. The last worker picks the next token and sends it back. Each worker keeps its own conversation state, so only a few kilobytes cross the network for each token.

The model's weights stay loaded on the workers; they are not sent over the network for each request.

Architecture

Sangama keeps three questions apart: who may join, how computers reach each other, and where the model runs.

                  +---------------------------------------------+
                  |                   Portal                    |
                  | invitations, signed membership, revocation  |
                  +---------------------------------------------+
                        |                   |                  |
                  signed membership list, checked every few seconds
                        v                   v                  v
                  +----------+        +----------+       +----------+
                  |  Client  | <----> |  Relay   | <---> | Workers  |
                  +----------+        +----------+       +----------+
                        |          (only when routers         ^
                        |           block a direct path)      |
                        +-------------------------------------+
                            direct encrypted connection
PartWhat it does
WorkerContributes memory and compute. Loads its share of the model and runs those layers.
ClientFinds workers, checks they cover the whole model, and runs requests through them.
PortalIssues single-use invitations, keeps the membership list, and revokes members.
RelayPasses encrypted traffic between computers when their routers block a direct connection. It never runs model layers and cannot read the traffic.
DiscoveryWorkers advertise which part of the model they hold, in signed records.

Every computer has its own Ed25519 identity, and all traffic is encrypted end to end (Noise over libp2p). Workers check every model file against a pinned SHA-256 list, so a route cannot silently use a different model.

A limit to know about: a worker can see the data it processes, so today's network is meant for trusted groups. Signatures prove who is a member, not that a computation was done correctly.

Results

New: Qwen3.5-397B on 20 GPUs, through a relay. The 397-billion-parameter model ran split across 20 rented GPUs with 16 GB each, every connection through a relay, at 1.8-2.6 tokens per second with identical output on every run. The GPUs did 21 ms of work per token; the network set the pace.

Measured on 29 September 2026 with the Qwen2.5-0.5B-Instruct test model, split across two workers. The full list of test scenarios and raw results is in the repository.

  • Same answer everywhere. At full precision, every combination produced exactly the same tokens: CPU, Apple Metal, NVIDIA CUDA and Vulkan, with either of the two engines, mixed in any order.
  • One machine, two GPUs: 103 tokens per second (220 with 4-bit weights).
  • Across the Internet: 3.1 tokens per second between a Mac on a home network and a GPU in a US datacenter, 260-370 ms apart. Distance, not computing power, sets the pace.
  • Through a relay: 7 out of 7 generations were exact over four minutes of continuous use, with every connection forced through the relay.

Speeds are single runs of a small test model and include network delay; they are not benchmarks. 4-bit output is only reproducible with the same weight file on the same kind of GPU, so a route must use one published file.

What the testing caught

  • GPU context bug: NVIDIA CUDA workers failed on every conversation after the first. Found, fixed, and re-tested over five conversations in a row.
  • Relay time limit: relay connections closed after two minutes, cutting off requests in progress. Raised to one hour; four minutes of continuous traffic then ran cleanly.
  • Mixed weight files: two differently compressed copies of the same model were accepted in one route. Workers now report a checksum, and such routes are refused.

Roadmap

  • Large open models. Qwen3.5-397B runs across 20 computers with 16 GB each (results). Next: make it faster with speculative decoding and nearby relays.
  • Published weights. Done: the model is published in per-layer slices with checksums, so each worker downloads only the layers it serves.
  • More hardware. Test runs on AMD, Intel, Qualcomm and Windows, then phones.
  • Nearby routes. Keep each route within one city or region, since network distance sets the speed.
  • Two home networks. The next acceptance test: two home routers, a relay, and direct connections through NAT.
